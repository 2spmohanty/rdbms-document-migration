Why MongoDB Atlas

Two architectures evaluated. One recommendation grounded in the engagement constraints.

The Query Problem
Multi-table JOIN vs single document fetch
Relational — current60ms p95
SELECT c.*, addr.*, prefs.*,
       la.balance, lt.tier,
       mc.opt_in, gdpr.consent
FROM   customers c
JOIN   addresses addr   ON addr.cust_id = c.id
JOIN   preferences prefs ON prefs.cust_id = c.id
JOIN   loyalty_accts la ON la.cust_id = c.id
JOIN   loyalty_tiers lt  ON lt.id = la.tier_id
-- ... across 45+ tables
WHERE  c.id = :id

Technology Comparison
Capability DynamoDB MongoDB Atlas
Access pattern flexibility Partition key constrains queries — new patterns need GSI redesign or backfill Index any field retrospectively — new pattern = new index, no redesign
Schema evolution Schemaless — new attributes added at write time Schemaless — new attributes added at write time
Vendor lock-in AWS only — no exit without full rewrite Multi-cloud. Open data model. Portable.
GDPR enforcement Global Tables — enforced at network and IAM layer Atlas Global Clusters — enforced at storage routing layer
CDC for migration DMS replicates Legacy RDBMS → DynamoDB directly DMS replicates Legacy RDBMS → Atlas directly
Migration path 45-table → single-table requires full access pattern redesign within budget constraint Document model maps naturally — Strangler Fig works without access pattern redesign

MongoDB Atlas — the natural fit

Migration Path Document model absorbs relational structure naturally. No single-table redesign. No access pattern commitment upfront.
Future-Proof Multi-cloud portability. Open data model. Index any field as requirements evolve.
GDPR at Storage Layer Atlas Global Clusters enforce residency at routing layer — architecturally harder to bypass than network controls.
